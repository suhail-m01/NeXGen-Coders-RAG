# The big-model experiment: settling two decisions that were made on a model too small to judge them

Two features in this project are fully implemented, fully measured, and shipped **off**:

| feature | flag | verdict at `qwen2.5:0.5b` | evidence |
| --- | --- | --- | --- |
| Contextual retrieval (situating blurbs written at ingest, prepended to the indexed text only) | `CONTEXTUAL_RETRIEVAL_ENABLED` | tied the gate 16/16, cost a correctness point, cost 1089 s of ingest against 23 s | `report_20261105_215324` (off) vs `report_20261105_223230` (on) |
| Structure-aware chunking with parent expansion | `CHUNKING_MODE=structure` | lost the gate 13/16, twice | `report_20261105_185025`, `report_20261105_185730` |

Both verdicts were reached in a 2 GB sandbox on `qwen2.5:0.5b`, because that is the only
model that fits there. `config.py`'s own default answer model is `qwen2.5vl:3b`.

So the true statement is **"these features did not help at 0.5b"**, and the statement that
is not supported by any measurement in this repository is **"these features do not help"**.
The difference is not academic. At 0.5b, a situating blurb is written by a model that
produced usable blurbs for **2 of 4** chunks in `project_notes.docx` and paraphrased,
preambled or refused the rest — `contextual.clean_blurb()` dropped them, and those chunks
were indexed as themselves. The feature was therefore not tested at 0.5b; a degraded
version of it was. Structure mode has the same problem from the other direction: its
chunks are assembled by rule, but the answers that failed were generated by a model that
also failed a plain CSV lookup.

This document is the protocol for re-measuring both on a machine big enough to run a real
model. The instrument is `scripts/experiment_big_model.py`.

---

## 1. What you need

* The Windows machine from `WINDOWS_SETUP_GUIDE.md`, working: Python 3.11–3.12, Ollama,
  Tesseract, the built index, `python scripts/selftest.py` at 258/258 (34 of those
  checks are this harness's own: its arm definitions, its verdict rule, its status
  derivation and its per-query movement detection are all tested offline, because a
  verdict rule nobody has tested is just an opinion with a table attached).
* One model pulled **before** you start, because the run itself must be offline:

  ```powershell
  ollama pull qwen2.5:3b      # text-only, ~1.9 GB
  ollama pull qwen2.5vl:3b    # vision-capable, ~2.9 GB - config.py's default
  ```

* Roughly 1–3 hours per model, with nothing else running. On a 4 GB card a 3B model plus
  an 8192-token KV cache may not fit; Ollama then falls back to CPU without complaining,
  and an hour becomes four. If the first gate comes back at minutes per query, stop and
  re-run with `--num-ctx 4096`.
* A **clean git tree**. The script refuses otherwise, and it is right to: a number that
  cannot be attributed to a commit is not worth the hours it costs to produce.

## 2. Which model, and in what order

Run `qwen2.5:3b` first. It is text-only, exactly like the 0.5b model every existing
report was taken with, so image ingestion stays identical and the reference arm is a
clean generation-quality comparison.

Then run `qwen2.5vl:3b` if you have the time, and expect a **third finding**: vision
changes ingestion itself. `images.py` builds the indexed content of an image item from
the model's own description (`content = build_representation(description, ocr_text)`,
line 158), and a text-only model produces no description — the PNG in the demo corpus is
currently indexed from OCR alone, with a `vision_ok=false` warning. A vision-capable
model rewrites that item, which changes image retrieval, image answers, and the
`image` row of the per-modality table. That is a real result, but it means the reference
arm is no longer a pure generation comparison, and the script warns you about it in
preflight rather than letting you discover it in the table.

Do not try a 7B model on a 4 GB card. It will run, on the CPU, and you will spend a day
to produce a latency column nobody can use.

## 3. The three commands

```powershell
cd C:\path\to\EvidenceAI

# 1. Read the plan. Touches nothing, needs no model, and prints what a real run would
#    refuse to do and why.
python scripts\experiment_big_model.py --plan --model qwen2.5:3b

# 2. Run all three arms.
python scripts\experiment_big_model.py --model qwen2.5:3b --yes

# 3. Read the result.
notepad evaluation\experiments\experiment_*.md
```

Useful variants:

```powershell
# Only the contextual question, reusing a reference arm you already ran.
python scripts\experiment_big_model.py --model qwen2.5:3b --arms contextual ^
    --reference-report evaluation\reports\report_XXXXXXXX_XXXXXX.json --yes

# Add the LLM-judge arm. Advisory only, four extra completions per answer, roughly four
# times slower - but at 3B the judge is no longer the content-blind scorer it was at
# 0.5b, so its opinion is worth having once.
python scripts\experiment_big_model.py --model qwen2.5vl:3b --judge --yes

# A rehearsal of the harness itself on the model you already have. The expected results
# are known, which is what makes it a test: the reference arm should reproduce
# report_20261105_224257, and the structure arm's retrieval figures should reproduce
# report_20261105_185730 (precision 0.3635, MRR 0.7031), because retrieval does not use
# the answer model at all.
python scripts\experiment_big_model.py --model qwen2.5:0.5b --arms reference,structure --yes
```

### The harness has been rehearsed against answers that were already known

An instrument that has never been checked against a known result is not an instrument. This
one was run in the build sandbox on `qwen2.5:0.5b` — the model every existing report was
taken with — so both arms had a published answer to reproduce.

| arm | report | result |
| --- | --- | --- |
| `reference` | `report_20261105_234615` | precision 0.3531, recall 0.9635, MRR 0.6458, citation accuracy 0.5635, correctness 1.0, groundedness 0.9375 — **identical on every gated metric** to `report_20261105_224257`, the report of record taken before this harness existed. Its retrieval-only pass, `report_20261105_234208_retrieval`, matched too. |
| `structure` | `report_20261105_235241` | precision 0.3635, MRR 0.7031, correctness 0.8542, and the same two queries failing — `Q10-absent-figure` and `Q16-paper-limitation` at correctness 0.0 — as `report_20261105_185730`, measured five hours earlier through a hand-run gate. Its retrieval-only pass, `report_20261105_234711_retrieval`, reproduced precision 0.3635 and MRR 0.7031 exactly, which is what it should do: retrieval never touches the answer model. |

Verdict: **KEEP OFF**, with three reasons printed — its own gate failed, it was below the
same-model reference on `retrieval_recall` (0.9635 → 0.9479) and `answer_correctness`
(1.0 → 0.8542), and four individual queries moved down. Afterwards the index came back
byte-identical (sha256 checked before and after, and checked again independently of the
script), and `baseline.json` had not moved.

The refusal paths were exercised as deliberately as the happy one:

* **Dirty tree** — exit 2, `REFUSING to start`, nothing modified.
* **A flag that never reached the data** — run with `CONTEXTUAL_MIN_ITEMS=99`, so
  `annotate_items` skipped every source and no blurb was written. The arm was abandoned
  with `blurbs is 0, expected >=1` rather than reported, exit 1, index restored. That is
  the failure mode that matters most, because the alternative is a confident comparison
  between two identical configurations.

What the rehearsal does **not** prove: anything about a 3B model. It proves the instrument
reads the same numbers a hand-run gate read, refuses to report an arm that did not happen,
and puts the index back the way it found it.

## 4. What the script does, arm by arm

| arm | configuration | compared against | answers |
| --- | --- | --- | --- |
| `reference` | the new model, shipped configuration | `evaluation/baseline.json` (`qwen2.5:0.5b`) | *what does the bigger model alone do?* — a **model** decision |
| `contextual` | + `CONTEXTUAL_RETRIEVAL_ENABLED=true` | the reference arm's own report | *does the feature help, at this model?* |
| `structure` | + `CHUNKING_MODE=structure` | the reference arm's own report | *does the feature help, at this model?* |

For each arm:

1. **Reindex** (`scripts/reindex.py --yes`) with the arm's environment. Every arm,
   including the reference: a flag that is not reindexed measures its own absence
   (see the comment at `rag_pipeline.py:287`), and a vision-capable model changes image
   items during ingest.
2. **Check the index against the arm** by reading SQLite, not configuration — the
   reference arm must have 0 blurbs and ≥1 table item, the contextual arm must have
   written ≥1 blurb, the structure arm must have built ≥1 parent. An arm whose flag never
   reached the data is abandoned with a message rather than reported.
3. **Retrieval-only pass** (`evaluation.py --retrieval-only`, ~30 s, no generation). This
   separates retrieval effects from generation effects, which matters because the two
   features fail for different reasons: at 0.5b, structure mode *improved* retrieval
   (precision 0.3531 → 0.3635, citation accuracy 0.5635 → 0.7323) and still lost the gate
   on answers.
4. **Full gate** (`evaluation.py --compare <target>`), then **verify the report against
   the arm**: the model, chunking mode and contextual flag are read back out of the
   report's own manifest, and a mismatch rejects the arm.

Configuration is changed **through environment variables only** — `config.py` resolves
environment → `.env` → default, so an arm's flags die with the arm. The script never edits
`config.py`, never writes `.env`, never passes `--save-baseline`, and records the sha256 of
`evaluation/baseline.json` before and after to prove it. The index is backed up before the
first arm and restored after the last, in a `finally` block, and the restore is proved by
hash: an interrupt or a crash leaves you with the shipped index, not an arm's.

## 5. How to read the result

The summary applies one rule mechanically and prints its reasons:

> Flip a default only when the arm **passes its own gate**, is **not below** the
> same-model reference on any gated metric, is **strictly better** on at least one, and
> **takes no individual query backwards** (status, correctness, citation accuracy,
> groundedness, recall).

A tie is not a win. Contextual retrieval tied 16/16 at 0.5b and still ships off, because a
tie buys nothing and costs eighteen minutes of ingest on every reindex.

Read these four things before the verdict:

* **The blurb rate** (contextual arm only): `N of M chunks got a situating blurb`. At 0.5b
  it was 2 of 4 in one document. If it is still under half at 3B, the feature is not being
  tested — the prompt is, and `contextual.PROMPT` is what needs work.
* **Ingest cost**, reference arm vs contextual arm. This is what the feature costs every
  time the corpus changes, and it does not shrink with a better model.
* **Per-query movements**, not just aggregates. The whole 0.5b groundedness improvement was
  one query (Q15's invented "Page: 8" disappearing), and the whole correctness loss was one
  query (Q7 answering both hops and dropping the required "87%"). An aggregate that moves by
  0.02 on 16 queries is one query, and you should know which.
* **Latency**, with its keep-alive policy. The script uses one `--keep-alive` for every arm
  so the column is internally comparable. It is *not* comparable to the reports quoted in
  the setup guide, which were taken with `OLLAMA_KEEP_ALIVE=0` in a sandbox that reloaded
  the model for every call.

## 6. What to do with each outcome

**The reference arm fails against `baseline.json`.** The model is a regression on its own,
before any feature is considered. Do not flip a feature default on top of it. Check
`--num-ctx 4096` (KV cache pressure), check that Ollama is not on the CPU, and if the
numbers are genuinely worse, keep `qwen2.5:0.5b` and say so — the guide already documents
that this project is sized for ≤4 GB of VRAM.

**A feature arm says `RECOMMEND ON`.** Then, by hand, in this order:

1. Flip the default in `config.py` (`contextual_retrieval_enabled = True`, or
   `chunking_mode = "structure"`).
2. `python scripts/reindex.py --yes` at the shipped configuration.
3. `python evaluation.py --compare` — the gate must pass at the *shipped* configuration,
   on a clean tree, and that run becomes the new report of record.
4. Keep **both** arms' reports in `evaluation/reports/`, as the 0.5b measurements were
   kept. The kit ships every report the documentation quotes by name.
5. Update the documentation that states the feature is off: `README.md` limitation 12
   (structure) or 14 (contextual), `WINDOWS_SETUP_GUIDE.md` §10, and the feature tables.
   State the model the decision was made at, and quote both report stems.
6. Rebuild the kit: `python scripts/build_kit.py --report <stems>`.

**A feature arm says `KEEP OFF`.** The decision stands, and the documentation gets stronger
rather than weaker: §10 and limitation 14 can then say the feature was re-measured at
`qwen2.5:3b` on the deployment target and is still off, with the numbers. That is a better
sentence than the one there now, which can only claim 0.5b.

**The two arms disagree with each other** (structure on, contextual off, or the reverse).
That is a legitimate outcome and the more interesting one. Do not enable both at once
without a fourth arm measuring the combination: they interact, because a blurb is written
for whatever chunking produced, and structure mode changes what a chunk is.

## 7. Things that will silently ruin the measurement

* **Comparing a 3B feature arm to the 0.5b baseline.** This is the mistake the harness
  exists to prevent, and it is why a feature arm with no same-model reference is refused
  rather than run. A model upgrade and a feature are confounded in that comparison, and the
  confound always favours whichever change you wanted to be true.
* **Promoting a 3B run to `baseline.json`** while the shipped default model is still 0.5b.
  Every later `--compare` would then gate the shipped configuration against numbers a
  different model produced. If you do change the default model, that is its own decision:
  promote deliberately, name the model in the commit, and re-measure both features after.
* **Trusting one run of one query.** Generation is not bit-reproducible at any model size,
  even at temperature 0 with `ollama_seed=42`. If a verdict turns on a single query, re-run
  that arm two or three times before believing it.
* **Comparing latency across keep-alive policies.** 14.3 s at `keep_alive=0` and 10.5 s
  with the model resident are the same machine and the same model.
* **Running the experiment on a dirty tree.** The reports would say `git_dirty=true` and
  nothing would be attributable. This exact thing happened during development and cost a
  re-run.

## 8. If it goes wrong

| symptom | cause | fix |
| --- | --- | --- |
| `REFUSING: model ... is not installed locally` | not pulled | `ollama pull <model>`; the run itself stays offline |
| `REFUSING: the working tree has N uncommitted change(s)` | dirty tree | commit, or `--allow-dirty` and accept `git_dirty=true` in the report |
| `REFUSING: arm ... sets X, which is not a config.Settings field` | a renamed or typo'd flag | fix `ARMS` in the script; the flag would otherwise have been ignored and the arm would have measured nothing |
| `ABANDONED: the index does not match what this arm declares` | the flag never reached ingest | read the arm's reindex log in `evaluation\experiments\logs\` |
| minutes per query | Ollama fell back to the CPU | `--num-ctx 4096`, close everything else, or use a smaller model |
| `HTTP 500` from Ollama | `OLLAMA_NUM_PREDICT=0` is rejected | leave it at the project default (512) |
| `THE INDEX DID NOT RESTORE CLEANLY` | a crash mid-restore | `python scripts/reindex.py --yes` rebuilds it from `data\` in under a minute |

Logs are per arm per stage in `evaluation\experiments\logs\`; the machine-readable result
is `evaluation\experiments\experiment_<stamp>.json`, and both are gitignored, like the
reports they cite.

## 9. Provenance

Every report this project ships records the commit it was taken at, whether the tree was
dirty, the model, the chunking mode, and the state of both feature flags
(`manifest.ingestion.pdf_tables`, `manifest.ingestion.contextual_retrieval`) — so a report
can be checked against the claim it is being used to support. The experiment JSON adds the
sha256 of `baseline.json` before and after, the sha256 of both index files, the resolved
configuration of every arm, and whether the index came back byte-identical.

One gap, stated rather than papered over: the build sandbox reset itself during
development and discarded the repository's commit objects. The tree was restored
byte-for-byte from the kit archive built at the previous HEAD, but the hashes named inside
older report manifests — `08856ef`, `46b48b3`, `dcb0138`, `9c49fc8` and the rest — no
longer resolve in this clone. Those reports are still valid measurements of this exact
tree; only their commit references are now unresolvable. Anything measured from here on
cites a commit that exists.
